Simulation overview

Goal

Simulation is one of two checks on the pipeline: the planted ground truth is known exactly, so it controls what real data cannot, which SNPs belong to which module. The other check, the external benchmark against Suzuki et al. (2024), is described in SNP biological clustering; the two are read together, not as a single pass/fail.

Simulations help with three levels of choice:

  1. What goes into the matrix (data, z-score compression) and the lFSR/magnitude membership gates.
  2. The validation cutoffs that decide a program’s confidence tier.
  3. Whether programs found separately in two traits can be linked, and in the right direction.

simulate_trait() generates a trait object of the same shape as trait(id, include_associations = TRUE) and plants structure over SNPs. The single-trait simulations come in two families — null (K = 0, no modules) and module (K > 0, planted modules) — so the same EBMF + validation pipeline can be tested for both hallucination (does it invent structure from randomness?) and recovery (does it find the structure we planted, and how well?). The multi-trait simulations, built on simulate_trait_pair(), test the linking step that follows.

Null simulations: testing hallucination

The null family keeps K = 0: no modules and no driver traits. The matrix is the dense target row plus unstructured background traits. Because there is no planted structure, any program of high or medium confidence is a false discovery, so the null runs measure how often the EBMF + validation battery invents structure from randomness.

  • The meaningful controls here are the background effect parameters (below) and noise_sd. The driver/module parameters (p_structural_zero, p_spurious, effect_tail, trait_overlap, snp_driver_groups, …) are inert when K = 0 because they only act on driver rows.
  • Key outputs: n_programs (how many factors EBMF proposes), n_valid_programs (how many reach high or medium confidence — the false-positive rate), and background_absorbed (the fraction of background SNPs pulled into valid programs — the SNP-level false-discovery rate).
  • The share of null programs in each tier is also reported. Almost every null program rests on one trait, so the single_trait share is how often noise passes the similarity test and lands in the tier that needs a closer look; the rest are low.

The null simulations, and how the rates change as the background is made denser, sparser, or stronger, are documented in Null simulation study of EBMF programs.

Module simulations: testing recovery

The module family plants K modules over SNPs and runs the identical battery on versions that differ along several axes of control. Each axis stresses a different way real data can depart from a clean block structure; the versions are generated by iterating the generative parameter arrays in the simulations vignette (Simulation study of EBMF programs).

Planted modules. K modules occupy SNP sets (disjoint by default). Each module has n_traits_per_module driver traits with effect_size-scale effects on its module’s SNPs, under a sign_pattern (coherent, flipped, or random). A driver trait is a row whose associations are localised to one module’s SNP block — this is the “signal” the EBMF programs are supposed to recover.

How we control the simulations. The parameters shape the input, and they differ in where the structure (or mess) they add lives:

  1. Background effect parameters (p_active_background, background_sparsity_sd, background_effect_scale) — the unstructured noise floor. Every background SNP association is an independent draw: p_active_background sets how often a background trait is observed at a SNP (density), background_sparsity_sd makes per-trait density heavy-tailed (most traits observed at a handful of SNPs, with a tail of denser traits), and background_effect_scale sets the magnitude of the hits relative to effect_size. Unlike modules, the background has no shared structure; it makes recovery harder by reducing the contrast between coherent module signal and unrelated associations.

  2. SNP driver groups and driver sharing (snp_driver_groups, driver_sharing) — the internal and cross-module SNP architecture of the planted modules. These parameters introduce additional structured complexity, rather than unstructured noise, but they act in different ways.

    snp_driver_groups partitions each module’s SNPs into groups and assigns each driver trait to only one corresponding SNP group. Thus, increasing snp_driver_groups progressively changes a planted module from a single coherent SNP-by-trait pattern into several distinct subpatterns. This is therefore a relatively strong form of within-module heterogeneity: at high values, the simulated data may contain multiple statistically distinguishable latent patterns even though all of their SNPs are labelled as belonging to the same ground-truth module. The parameter consequently tests how many distinct subpatterns can be embedded within one nominal biological programme before EBMF and subsequent clustering resolve them as separate factors or programs.

    driver_sharing acts differently. It does not control similarity between SNP groups within the same module. Instead, the first floor(n_traits_per_module * driver_sharing) driver traits of module m are also active across the SNP set of the previous module. It therefore creates structured overlap in SNP usage between adjacent modules: a driver trait nominally associated with one module can also generate signal among SNPs belonging to another module. This differs from both trait_overlap, which makes modules share driver traits themselves, and the background parameters, which generate associations without coherent shared structure.

  3. Module trait overlap (trait_overlap, trait_effect_corr) — the overlap of trait signatures between modules. trait_overlap determines the proportion of each module’s driver traits that are shared with other modules. As trait overlap increases, different modules are defined by increasingly similar sets of traits, reducing the distinction between their pleiotropic signatures. trait_effect_corr determines how similar the corresponding effects are when traits are shared: shared drivers can have correlated but non-identical effects across modules.

    This manipulation is distinct from driver_sharing. trait_overlap changes which traits define each module, whereas driver_sharing changes which SNPs are affected by particular driver traits. At high trait overlap, modules may become difficult to separate because their trait signatures are genuinely similar, even when their SNP sets remain distinct. The parameter therefore tests the resolution limit of the method when biologically distinct SNP groups have increasingly overlapping pleiotropic profiles.

  4. Spurious hits (p_spurious) — contamination of the driver signal. p_spurious adds background-scale off-module associations to driver traits, introducing associations outside their intended structured SNP patterns. Unlike snp_driver_groups or driver_sharing, these hits do not represent additional coherent latent structure. They instead test robustness to isolated or weak associations that partially obscure the intended module boundaries.

The module simulations are scored against ground truth by evaluate_univariate_simulation():

  • module_recall — for each planted module, the largest fraction of its SNPs contained in any single predicted program (fair to overlapping/merged programs).
  • coverage — fraction of all SNPs placed into valid programs.
  • background_absorbed — fraction of unstructured background SNPs absorbed into valid programs (higher = more hallucinated structure).
  • ARI (ari_all, ari_structured) — adjusted Rand index against the planted partition, using each SNP’s strongest program as a hard projection.

The module and null runs are read against each other: the module runs show how much planted structure is recovered, and the null runs supply background_absorbed as a false-discovery rate — how much of what is recovered under no planted structure is invention.

Multi-trait simulations: testing correspondence

The multi-trait analysis (Multi-trait EBMF program correspondence). Programs are found separately for each target trait, with the single-trait pipeline (SNP biological clustering), and two traits’ programs are linked by the congruence of their trait profiles, graded with the alignment of their SNP loadings at the loci the traits share (compare_program_pairs_loadings()). The simulation study below was run with an earlier, locus-only link rule (a pair sharing at least 3 high-confidence loci whose concordance survives the FDR threshold) and has not yet been re-run with the profile-based tiers, nor with the current rule, which grades a strong profile match by whether the shared loci agree, disagree or are too few to check (locus_status).

Simulation study of multi-trait program correspondence checks this pipeline where the answer is known. Its most important aspects:

  • Design. simulate_trait_pair() plants one program in both traits (K_shared = 1) and K_specific programs in each trait alone, over unstructured background studies. The shared program has the same driver studies in both traits. Two things vary: the SNP overlap, the fraction of the shared program’s loci that are the same locus in both traits (0.1 to 1; at 0.1 the two copies share 4 of 36 loci), and the direction, concordant or antagonistic. A null version shares nothing, so every link is false.
  • The same pipeline as real data. Each trait is fitted and validated on its own; EBMF never sees the other trait. Linking is then run twice, on every fitted program and on the valid programs only, so the effect of the validation gates on linking can be seen.
  • Three questions, scored separately.
    1. Discovery: is the shared program found valid in each trait? If not, the status of the best-matching program says which gate removed it. Fitted programs are mapped to planted ones by SNP Jaccard (at least 0.1), and the match is scored by SNP precision, SNP recall and the correlation of the loadings with the planted per-locus effects.
    2. Linking: recall (the shared program was linked) and precision (the links reported were real). A link is a pair sharing at least 3 high-confidence loci whose concordance survives the FDR threshold.
    3. Direction: among real links, the share called in the planted direction.
  • Orientation hides antagonism from the loadings. Each trait’s loci are oriented to its own risk allele before fitting, so a shared locus loads positively in both traits’ programs whatever the direction. The sign of the concordance statistic therefore cannot express antagonism; module_rg() can, because it works in a common allele frame. It needs at least 10 usable shared loci and a confidence interval that excludes 0, so links resting on fewer or weaker loci get no direction (undetermined), in simulation and on real data.
  • Overlap sets a floor on detection. Links are scored on loci only, so a program shared at entirely different variants (overlap 0) cannot be linked by design. At overlap 0.1 the copies share 4 loci, just above the 3 a link needs, which is where recall is expected to fall.
  • Limits. Each planted program is isolated (its own drivers and loci), and the background is unstructured by default, so the fits are easier and the false-link rate more optimistic than on real data. Recall is credited per planted program, not per link, so a program EBMF splits in two is not rewarded.
